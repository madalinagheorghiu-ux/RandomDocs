One Visual Identity, One Owner

Where Theme, Branding, and Fonts should live in the FlowX platform

Author: Madalina Gheorghiu  ·  Date: 2026-08-06  ·  Evidence base: field-level audit of the designer codebase (references in Appendix)

1Executive summary

A solution's visual identity — what end-users actually see — is one job, owned by one persona: the configurator. Today that job is fragmented across two permission scopes (Organization vs Workspace), three surfaces (Theme, Branding, UI Designer), and three different data models for the same concepts.

The audit question is not "where should Themes vs Branding vs Fonts live?" It is:

Can the persona accountable for the end-user experience complete the visual-identity job without a hand-off?

Today the answer is no — and the codebase shows the split is historical, not intentional:

  • 6 of Branding's 8 fields duplicate Theme concepts (colors, background, header layout, shadow) in a flat, lossy, unreconciled copy.
  • The header is configurable in three places with three incompatible models (Branding, Theme's mobile-only navigation section, UI Designer's HEADER element).
  • The two Fonts pages are literally the same component, service, and API mounted twice behind different permission guards — the duplication is pure navigation, not functionality.
  • The code itself flags the debt: the Themes route carries a TODO: Temporary, long term this might not stay here, and Branding's config code is hard-coded 'default' with a comment promising future multi-config support.

Recommendation in one line: keep the Org/Workspace permission boundary, but re-sort the specs so that Org = governance & defaults (font library, default theme, portal/listing branding) and Workspace/Solution = everything that shapes a specific solution's experience (theme, solution header via UI Designer, background), with inheritance downward so nothing starts blank and nothing is defined twice.

2Current state — what the code actually says

2.1 Theme (Workspace · cms/themes)

A deep, tokenised, platform-aware model — clearly the platform's "real" visual identity system:

  • Shared color tokens (primary/secondary/success/warning/error/neutrals, each with 11 shades, light+dark)
  • Per-platform (web / Android / iOS): typography tokens, shadow tokens, general settings (incl. appBackground, accent color, 7 font-role assignments), and ~40 component sections (button, inputs, table, modal, chat, navigation, …)
  • Compiled server-side per platform and applied by the renderer
  • Inheritance exists inside a theme; duplication exists inside a workspace ("Copy of X"); the only cross-workspace path is manual export → import
  • A new workspace gets no usable theme by default — only the backend-seeded system theme; there is no org-level default-theme cascade

Code signal: the themes route is annotated // TODO Theming: Temporary, long term this might not stay here. — its current placement is acknowledged as provisional.

2.2 Branding (Organization · organisation-admin/branding)

Eight flat fields, applied client-side as CSS variables on the generic container app:

showHeader · logoUrl · shadow {blur, color, alpha} · headerLayout {height, 4×padding} · primaryColor · secondaryColor · headerBackgroundColor · backgroundColor

  • One config per org, hard-coded (configCode = 'default', with a code comment: "This will be changed when we will support multiple configs per organization")
  • No favicon field exists anywhere in the platform
  • No typography/fonts in branding
  • The container app's header appears not to consume logoUrl at all — it imports a static FlowX SVG (needs verification; if true, the logo override is silently broken)
  • Colors are single hex values — a lossy shadow of the theme's 11-shade token scale
  • Shadow is a lossy subset of theme shadows (no x/y/spread)

2.3 Fonts (both Org and Workspace)

Same list component, same detail component, same store, same service, same API endpoints (cms/api/fonts/*). The only difference is routing and permission guards (org_font_* vs wks_font_*); scoping happens via an HTTP header, not the URL. The "two places" are one feature with two doors.

3The problems, stated as user pain

P1 · CORE PROBLEM

The accountability / permission mismatch

The configurator is accountable for what end-users see, but Branding sits behind org_config_edit. Every branding change is a ticket to an org admin — a hand-off with no preview, no ownership, and no way for the configurator to verify the result. For the most brand-sensitive part of the experience (the shell customers see first), the person who owns the outcome has the least access.

P2

Split-brain visual identity

Primary color, secondary color, background, header background, shadow: each is defined twice — once in Theme (tokens, per-platform, server-compiled) and once in Branding (flat hex, CSS vars, client-side). Nothing reconciles them. A configurator can perfect the theme and still ship a solution whose shell clashes with it, because the shell reads a different, org-owned copy of "the brand."

P3

The header lottery

To control the header, a user must understand three models and their interaction: disable the container header in Branding (org admin needed), then build a HEADER element in UI Designer (which has layout but no content/branding model), styled via a theme section that is mobile-only for navigation. The current workaround — disable the container app to avoid two headers — is the UI equivalent of turning off the feature to fix the feature.

P4

Cold-start workspaces

A new workspace starts theme-less even when the org already has a perfected theme next door. The only reuse path is export → import — a manual file round-trip for something that should be a default. This punishes exactly the orgs that scale (more workspaces = more re-setup).

P5

Duplicate doors, one room (Fonts)

Same list in two navigation locations teaches users the wrong mental model ("are these different font sets? do I need to upload twice?"). The duplication exists to solve an access problem (configurators can't reach Org Settings) — it's a permission patch expressed as information architecture.

P6

Multi-brand orgs are structurally impossible

Tenancy is mixed: some orgs are one brand, some host solutions for multiple client brands, and per-solution standalone containers exist. A single hard-coded org-level branding config cannot serve the multi-brand case at all — there is no per-solution or per-workspace branding override.

P7

Branding under-delivers even on its own promise

No favicon. Logo override apparently unread by the container header. Lossy shadow. Single flat hexes. As a "white-label the shell for your client" feature, it's incomplete — and its gaps can't be patched by the workspace-level theme because the two systems don't talk.

4Design principles (the argument's spine)

1
Ownership follows accountability.Every spec that shapes a solution's end-user experience must be reachable by the configurator, without an org-admin hand-off. Org Settings is for governance (what's allowed, what's default), not for design work.
2
Define once, inherit down.Org sets defaults and shared assets → workspaces inherit them automatically → solutions may override where it matters (standalone containers, client-specific brands). Nothing starts blank; nothing is authored twice.
3
One concept, one home.Each visual concept (header, background, color, font) has exactly one authoring surface; other surfaces may read or reference it, never redefine it.
4
Theme is the single source of visual truth.It is already the richest, platform-aware, token-based model. Branding-type needs should become consumers of theme tokens, not a parallel flat copy.

5Recommendation — target model

Keep the Org/Workspace permission boundary (fixed constraint). Move specs, not scopes.

5.1 Org Settings → becomes "Governance & Defaults"

KeepsWhy
Font library (canonical, single)Fonts are licensed org assets; org-wide availability is the point. Already technically one list — make the IA say so.
Default theme designation (+ optional org theme catalog)Org decides what new workspaces start from. Fixes P4 without moving Theme itself.
Portal branding (the listing page where clients see all solutions)The portal is genuinely tenant-wide: logo, listing background, favicon (to be added). This is the legitimate residue of today's Branding page.

5.2 Workspace → remains the theme home, gains what it's missing

  • Theme stays at workspace level (validated: configurators without org access must own it) — but new workspaces inherit the org default theme (linked copy or reference — see Q1).
  • Theme gains a web Navigation/Header section (today mobile-only) so the solution shell's look is themable like everything else.
  • Fonts page at workspace level remains as a read/manage view of the org library — one entity, clearly labeled ("Organization font library"). No behavior change needed; only labeling and IA honesty.

5.3 Header → one home: UI Designer

The global navigation element in UI Designer becomes the single authoring surface for the solution header.

  • Extend the HEADER element with the content model it lacks (logo slot, title, nav items) — today it's layout-only.
  • Its styling binds to theme tokens (the new web navigation section) — consistent with every other component.
  • Branding's header fields (showHeader, headerBackgroundColor, headerLayout, header shadow) are deprecated: the container app either shows the solution-defined header or its minimal portal chrome. The "disable the container to avoid two headers" workaround disappears because there is only one header definition.

5.4 Branding page → renamed & reduced to "Portal settings"

What remains org-level is only what is genuinely org-scoped: portal logo, portal listing background, favicon, legal/footer bits. Everything solution-facing (colors, backgrounds, header) is served by theme + UI Designer. For multi-brand orgs / standalone containers, the solution's own theme + header simply are the branding — no org bottleneck, no parallel model.

6Assumptions to validate

  • A1. Configurators consider the container-app shell "their" responsibility (not a platform-team concern). Validate with 3–5 configurator interviews.
  • A2. Org admins experience branding requests as toil, not as a control point they want to keep. If they want governance, solve it with an approval/lock on theme sections, not with feature placement.
  • A3. The backend can scope/compile theme tokens for the container app (today the container is a React app reading CSS vars; themes are compiled per-platform elsewhere).
  • A4. logoUrl really is unread by the container header (code suggests a static SVG import) — verify before citing in the pitch.
  • A5. No customer depends on divergent fonts per workspace (the API appears org-scoped either way, likely safe).

7Open questions

  • Q1 — Inheritance semantics: when a workspace inherits the org default theme, is it a live reference (org edits propagate — risky) or a fork at creation (safe, but drifts)? Recommend: fork + "update available" signal.
  • Q2 — Governance counter-need: do some orgs want to lock brand specs against configurator edits (banks)? If yes, the answer is per-section theme locking, not org-level feature placement.
  • Q3 — Migration: existing orgs with configured Branding — map their 8 fields into theme tokens automatically, or run dual systems during a deprecation window?
  • Q4 — Portal identity vs solution identity: when one org hosts multiple brands, whose brand does the portal listing page wear? (Argues the portal is org-chrome — exactly why it stays in Org Settings.)
