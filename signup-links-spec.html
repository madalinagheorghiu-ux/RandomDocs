The brief

What we're building

An Organization Admin generates a registration link that lets a person create their own end-user account and be granted access to a Solution automatically, with a role the admin chooses. Joiners can be screened by email verification, a join code, or an admin approval step. The link can be revoked or regenerated at any time.

The point is to remove the requirement to know an end user's email address before they can be onboarded.

Your requirement is an open join link with enterprise screening controls. That combination is the gap in the market — no product does both well, and none does it per-role.

Every implementation reviewed is one of three shapes, determined entirely by who the link is addressed to. Consumer and education tools ship open links but almost no screening. Enterprise IAM ships rich screening but assumes you know who's coming. Only Moodle and Discord model the link as an object you can have several of — and neither has an approval gate.

Terminology — settled

Organization Admin is the FlowX platform role: creates the org, adds configurators, owns registration-link policy and the kill switch.

Solution Admin is a role inside a built Solution — for example the person who approves what professors upload. It is an end-user role, not a FlowX platform role.

These are two different approvals with two different queues. Keep the vocabulary separate everywhere in the UI, or the first customer will conflate them.

A second axis — when the role is decided

Addressing is one axis. The other is timing, and it cuts across all three archetypes:

  • Role-per-link — the role travels with the link, granted at the moment of joining. Moodle, Discord community invites, Auth0's roles array, Power Pages web roles.
  • Role-after-join — everyone lands as a default member and is sorted afterwards, by an admin or by an onboarding questionnaire. Slack, Discord's membership-screening and onboarding flows.

Role-per-link is the right fit here, and it isn't a close call: access becomes deterministic and auditable, the joiner sees what they're getting before they commit, and nobody lands in a Solution with the wrong permissions while waiting to be sorted. Role-after-join also forces a second manual step, which is exactly the cost this feature exists to remove.

A · Targeted invitation — what we're replacing

Auth0 Organizations invites by email; the link lets someone create an account or log in and join, and roles can be predefined on the invitation — but the assigned role only applies when logging in via that organization, and the joiner must use the exact invited address. Auth0 has since added self-service sign-up as an explicit alternative, which tells you email-first onboarding wasn't enough for their customers either.

Power Pages is the closest existing analogue. The admin generates an invitation code that carries additional web roles granted at redemption, and the docs state plainly that the user doesn't need to supply an email address because they've already provided the code. That is your requirement, solved — except codes are generated per contact record, so it doesn't scale to "publish one link for 300 students."

Keep targeted invitations. They stay the right tool for the three named professors. The new link is for the 300 students.

C · Policy-based self-service — where the screening lives

Okta allows or denies self-registration per policy, auto-adds registrants to groups, requires email verification before the account can reach any app, and can validate the email domain to deny public email providers. That last rule is the highest-value screening control for an institution: block gmail.com, allow the university domain.

Entra External ID exposes API connectors at defined points in the sign-up flow, documented for exactly your three gates — validate input against a permitted list, run identity verification, and route to a custom approval system that can auto-approve or send to manual review before the account is provisioned. The lesson is architectural: don't hardcode the screening steps, make them extension points.

Clerk names the two approval postures cleanly — automatic invitation (matching users are auto-joined) versus automatic suggestion (users request to join and an admin must approve). Same rule, two frictions. A screening rule shouldn't decide whether someone can join; it should decide how much friction they meet.

Keycloak matters because it's our IdP. Realm settings expose a User registration toggle plus default roles and default groups for self-registered users — but it is realm-wide and static. The docs themselves say that role assignment driven by business logic requires an external service calling the Admin API. That single constraint decides our architecture; see below.

Reference 03 — the admin mental model

Atlassian · one control, four postures, open to closed

The cleanest admin abstraction in the study. Rather than a scatter of independent checkboxes, joining policy is a single setting with four mutually exclusive values, ordered from most open to most closed — so an admin can read their security posture off one line.

Differentiation

What the market gets wrong

Five recurring failures. Each one is a design requirement for us, and the first two are documented user complaints against the education incumbents.

1

Open link with no approval option

Google Classroom auto-enrols anyone holding the class code, and the most-upvoted request in its community forum is for teacher approval on code joins. Canvas has the same hole. Shipping an open link and an approval gate on the same object puts us ahead of both LMS incumbents on day one.

2

Silent joins

Canvas's own documentation states that instructors are not notified when a student self-enrols. This is the difference between a feature admins trust and one they switch off — and we already have a Notification Center to hang the digest on.

3

One link per container

Figma, Miro, Slack, Classroom and Canvas each allow exactly one link per team or course. A professor link and a student link simply cannot coexist. Only Moodle and Discord model it as a list.

4

The link is a setting, not an object

When the link is a checkbox on a settings page you cannot name it, expire it, cap it, audit it, or run two at once. Modelling it as a first-class object costs nothing at design time and unlocks every other requirement.

5

Unbounded by default

Discord and Slack both learned this the hard way; Slack now hard-caps every invite link at 30 days and 400 uses. Default to bounded and make "forever, unlimited" a deliberate opt-out.

The agenda

Ten decisions — two settled, eight open

Each decision names who makes the call and what it blocks, so the meeting can be run down the list. D1 and D5 are closed and kept here with their reasoning; the rest are the agenda. D2 should be taken first — everything else depends on it. D10 came out of drawing the journeys, which is the usual way a missing decision surfaces.

D1

Does the admin approval gate ship in V1, or later?

Settled: approval ships in V1. Approval is the single documented gap in both education incumbents — the top community request against Google Classroom and the same hole in Canvas. It is also the only V1 item that makes a link safe enough to grant a non-trivial role, and without it the Reviewed preset can't exist at all, which in turn means no link can grant Solution Admin.

Recorded for whoever reads this later: the second research pass put approval in Phase 3, behind join codes, expiry and the pause state. That position wasn't unreasonable — the approval queue is the most UI-expensive item in V1, and it's the obvious thing to cut if V1 has to shrink. It just isn't free: cutting it takes the Reviewed preset and elevated-role links with it.

Decided 13 AugProduct leadV1 scope confirmed

D2

Keycloak-native registration, or a FlowX-owned flow?

Keycloak's own self-registration is realm-wide with static default roles, and Keycloak Organizations' invitation links are email-bound. Neither expresses "this joiner gets Student, that one gets Professor."

Recommend FlowX-owned. Keycloak stays the credential store; we serve the landing page and call the Admin API. It's what Keycloak's own docs advise for business-logic-driven role assignment, and it's the only option that gives per-link roles, per-link screening and tenant branding. Full comparison in Architecture.

Engineering lead decidesBlocks: everythingDecide first

D3

How do we stop an elevated role being minted from an open link?

Three mechanisms: an explicit Organization Admin allowlist of which roles are link-joinable per Solution; automatic detection from the role's permission set; or forcing the Reviewed preset on elevated roles.

Recommend the allowlist as the primary control, with detection as a safety net. The allowlist captures admin intent and is auditable — Google Classroom does exactly this by making co-teacher a role its links can never grant. Detection alone is a rule the product infers, which will be wrong on some customer's role model. Both, with the allowlist winning.

Product + EngineeringBlocks: permissions modelBlocks: create-link UI

D4

Is the token hashed at rest, or encrypted and re-revealable?

Hashed with a one-time reveal is strictly stronger. Encrypted-at-rest lets an admin re-copy a link they already distributed.

Recommend encrypted and re-revealable. A link that can't be re-copied gets pasted into a shared doc the first time an admin needs it twice — which is a worse security outcome than the one we'd be defending against. Security should have the final say.

Engineering + SecurityBlocks: storage schema

D5

What do we pre-fill for expiry and max uses?

Slack hard-caps every link at 30 days and 400 uses. Discord defaults to a 100-use cap — a documented growth-killer when admins don't notice it and joins silently stop.

Settled: bounded defaults, made loudly visible. Discord's failure isn't the cap, it's the silence. Pre-fill 30 days / 100 uses; show remaining uses and time on the link row at all times, not behind an edit screen; notify the owner at 90% of max uses, on exhaustion, and on imminent expiry with recent activity. "No limit" stays available as an explicit, warned opt-out.

This is the one place where a safe default is actively dangerous if it's quiet — a capped link that stops admitting people looks identical to a link nobody is clicking. Visibility is the feature; the cap is just the mechanism.

Decided 13 AugProduct leadFeeds: notification rules

D6

Is a link scoped to a Solution or a workspace — and what happens across versions?

A Solution has versions and branches. cas_runtime_role is org-scoped, which may force an explicit application_id on the assignment regardless of what we choose.

Recommend Solution scope, following the Solution across versions, keyed on application.id rather than global_id — the former is preserved across workspace forks. Needs confirming against how runtime roles are actually scoped before it's more than a preference.

D7

Does the per-link redirect land in V1?

A URL configured on the link that drops the joiner straight into the role's entry screen rather than a generic console. Keycloak does this on invitation acceptance.

Recommend yes. It's a single nullable field and a redirect, and it's the difference between "you're in" and "you're in, now find the thing you came for." Cheapest quality-per-point item in the whole plan.

D8

Can one person hold end-user accounts in two organizations with the same email?

cas_user.username is unique per org; subject_id is globally unique. So the answer is decided on the Keycloak side, not by us.

No recommendation — this needs a factual answer before the "existing user" path can be coded. It determines whether clicking a link while already signed in to another org creates, links, or rejects.

D9

What happens when a link would push the org past its seat entitlement?

Block the join, let it through and warn, or queue joiners until seats free up. Atlassian's docs are explicit that link joiners consume paid seats.

Recommend warn at creation, block at redemption — show remaining seats when the admin sets max uses, and give the joiner a clean "this Solution is full" dead-end rather than a half-provisioned account. Queuing sounds friendly and creates a support burden nobody has asked for.

Product lead decidesBlocks: entitlement integration

D10

One URL per role, or one URL that offers a choice of roles?

Distribution wants a single address to put on a poster. Security wants each role to keep its own screening, cap and audit trail. These sound opposed and aren't.

Recommend a role-selector page that fans out to the underlying links. One public URL per Solution shows "Join as Professor" / "Join as Student"; each button is a distinct registration link with its own preset, limits and attribution. Only Organization-Admin-allowlisted roles appear, so an elevated role is never a button that exists. The joiner picks between published options, which is not the same thing as choosing their own role — no product reviewed allows the latter, and it would let anyone award themselves Solution Admin. Cost is one extra page; the entity model is unchanged.

Implementation · 01

The core model

The one decision everything hangs off

A Registration Link is a first-class, revocable object owned by a Solution, that mints end-user accounts with exactly one runtime role.

Not a setting. Not a property of a role. An object, in a list, with a lifecycle. N links per Solution means the professor / Solution Admin / student requirement falls out for free; each link carries its own expiry, cap, screening and audit trail; and a leaked student link doesn't force rotation of the professor link.

RegistrationLink
  id                    uuid
  organization_id       uuid          -- tenant scope
  workspace_id          uuid          -- the Solution's workspace
  application_id        uuid          -- the Solution
  name                  string        -- "Autumn 2026 students"
  token                 string        -- URL segment, high-entropy
  join_code             string?       -- optional 6-8 char typed code
  granted_role_id       uuid          -- exactly ONE runtime role
  granted_group_ids     uuid[]

  -- screening
  require_email_verification  bool    (default true)
  require_join_code           bool    (default false)
  require_admin_approval      bool    (default false)
  allowed_email_domains       string[] -- empty = any

  -- bounds
  expires_at            timestamp?    -- null = never, must be opt-in
  max_uses              int?          -- null = unlimited, must be opt-in
  use_count             int

  -- lifecycle
  status                ACTIVE | PAUSED | EXPIRED | EXHAUSTED | REVOKED
  rotated_from_id       uuid?         -- regeneration lineage
  created_by, created_at, revoked_by, revoked_at, revoke_reason

RegistrationAttempt                -- one row per person who used the link
  id, registration_link_id, email, submitted_at,
  status: PENDING_VERIFICATION | PENDING_APPROVAL | APPROVED
          | REJECTED | COMPLETED | EXPIRED,
  decided_by, decided_at, reject_reason,
  resulting_user_id     uuid?,
  ip, user_agent                      -- abuse forensics

One role per link, deliberately

A link granting a set of roles is a link whose blast radius you can't read at a glance. If an admin needs two roles for one cohort, they compose a group. It also keeps the joiner's landing page honest: "You're joining Intro to Biology as a Student."

Lifecycle

ACTIVE⇄ PAUSED· EXPIRED· EXHAUSTED→ REVOKED→ new ACTIVE link
  • PAUSED is the cheap reversible stop. Most "security concern" moments are really "pause while I check" — give admins this so they don't burn a link they'd have to redistribute.
  • REVOKED is terminal. Never reactivate a revoked token; that's the entire point of revocation.
  • Regenerate = revoke old + create new with identical config, in one action, one audit entry, rotated_from_id preserved. This is Figma's "Reset invite links", and it matters because two separate steps leave a window with no working link.
Say this in the UI

Users already onboarded through a revoked link keep their access. Revocation only stops future joins. This is the single thing admins get wrong about every product in this study. Offer "also remove the 47 people who joined via this link" as a separate, clearly-labelled destructive action.

The screening gates

Present them as Atlassian's ordered ladder, not a checklist — Open (verification only, for a lecture hall), Code-protected (verification + code, the default, for a link posted somewhere semi-public), Reviewed (verification + approval, for professors or anything with elevated permissions). "Custom" holds the raw gates behind a disclosure.

Hard product rule

Any link granting a role with administrative or approval permissions inside the Solution — Solution Admin, for instance — must be forced to Reviewed. Detect it from the role's permission set and block it at save time with a clear reason. An Organization Admin should not be able to publish an open link that mints approvers.

Implementation · 02

Where this lands in FlowX

Grounded in the actual platform: Keycloak realms, the cas_runtime_* hierarchy, and SpiceDB.

This is entirely a runtime-authorization feature

End users live in the user Keycloak realm, and cas_user.subject_id is the Keycloak subject. Runtime end-users are not designer users — the runtime hierarchy lives in the parallel cas_runtime_* tables (cas_runtime_role, cas_runtime_group, cas_runtime_role_assignment, cas_runtime_user_*), org-scoped rather than workspace-scoped, with a system-seeded All end-users group per organization. Nothing here touches cas_user (designer_user = true).

The Keycloak constraint decides the architecture

Keycloak's built-in self-registration is realm-wide with static default roles and groups. It structurally cannot express "this registrant gets Student, that one gets Professor."

Keycloak Organizations doesn't close the gap either, and it's worth being precise about why, because at first glance it looks like it does. Organizations support member registration via invitation links: if the invited email has no account, the link drives the realm's self-registration flow — and invitation-only self-registration (registration closed except via link) landed in 26.0 after community demand. But the invitation is bound to the email it was sent to, which is the exact constraint this feature exists to remove. It also carries a documented lifecycle gap: there is no pending-invitation visibility, with invitations described by contributors as disappearing "into the void" — tracking had to be contributed upstream by a third party.

What that tells us

Reuse the IdP's registration and email-verification machinery. Own the invitation lifecycle state in the product layer — status, usage count, attribution, audit. The gap Keycloak had to be patched for is precisely the RegistrationLink registry we're proposing, so we'd be building it regardless of which option below we pick.

Take B. It's what Keycloak's own documentation recommends for non-trivial cases, and it's the only option giving per-link roles, per-link screening and tenant branding. Keycloak stays the credential store; FlowX owns the flow.

Service ownership and the two auth contexts

authorization-system is the natural owner: it already owns cas_runtime_*, and it is the only service that writes SpiceDB tuples and keeps Postgres and SpiceDB in sync. Role assignment on join is exactly a tuple write, so it must go through this service rather than around it.

  • The redemption endpoints are unauthenticated by definition — the joiner has no account yet. They sit outside the normal @CASAuthorize path and need their own hardening. This is the highest-risk surface in the feature; treat it as public internet.
  • The management endpoints use @CASAuthorize at ASSET or WORKSPACE allocation level, so a configurator scoped to one workspace cannot mint links for another.

Provisioning sequence

Keycloak and Postgres are separate stores, so this needs compensation, not a transaction:

  1. Validate the link — status, expiry, max uses, domain, code. Read-only and cheap.
  2. Create or locate the Keycloak user via the Admin API, using an SA token.
  3. Create the cas_runtime_user row bound to subject_id + organization_id.
  4. Assign granted_role_id, add to granted_group_ids and the org's All end-users group.
  5. Write SpiceDB tuples.
  6. Increment use_count atomically.
  7. Emit the notification event.
Known contract gotcha

If step 3 fails after step 2 you have an orphaned Keycloak user. Either compensate or make step 2 idempotent and reconcilable — pick one and write it down. Note that CAS user-delete returns 400 with error.validation.user.not_found for a missing user, not 404, so compensation logic must tolerate that and must not classify it as a server failure.

Two cases that will otherwise bite

The person already has an account. Someone clicks a student link but is already an end-user in the org. Don't create a second account and don't fail — ask them to log in, grant the role to the existing cas_runtime_user, and record the attempt against the existing user. If they already hold a higher role, say so and no-op rather than silently downgrading them.

Seats. Atlassian's warning applies directly: users who join via a link consume licensed seats. Check entitlement before provisioning and show remaining seats on the link management screen. An admin publishing a link to 500 students should learn about the 100-seat limit at creation time, not from an invoice.

05Allowlist joinable roles

Per solution: Professor ✓, Student ✓, Solution Admin ✗. The master switch — configurators work inside it.

Decision D3
06Watch the registry

Every live link across every solution, with usage, creator and a join digest. Accountability, not approval.

07Hold the kill switch

Disable every registration link org-wide in one action, no per-link cleanup.

Incident path
FlowX · Configurator

Builds the solution, then opens the doors to it

Steps 1–4 are the existing build flow. The new work is steps 5–8, and note step 5: the configurator doesn't decide which roles are joinable, they discover what the Organization Admin already permitted.

01Accept the invite

Lands in the workspace with a designer account, scoped to that workspace only.

02Create the project

The project, packaged, is the Solution — the unit end users are granted access to.

03Build it

Processes, screens, integrations, resources. Unchanged by this feature.

04Define end-user roles

Professor, Solution Admin, Student — each with its permissions inside the solution.

05See what's joinable

Only allowlisted roles can get a link. Solution Admin shows as blocked, with the reason and who can unblock it.

06Create one link per role

Name, role, screening preset, limits, and where the joiner lands. One role per link, always.

Decisions D5, D7
07Publish & get the URLs

The solution's login URL, plus the sign-up link, join code and QR for each role.

08Run the doors

Registry, approval queue, pause, regenerate, revoke — for their own solution only.

End user · Professor

Sign-up — from a link to inside the solution

The whole point: nobody had to know this person's email address in advance. Two branches, both common — an existing account at step 3, and the approval hold at step 7.

01Gets the link

Email, poster, QR on a slide, LMS post. No invitation, no admin knowing their address.

02Opens the landing page

Branded. "You're joining Northbank Grading as a Professor," what that role can do, and what happens next.

03Already have an account?

Yes → log in, gain the role, skip to step 8. No → continue. Never a duplicate account.

Branch
04Enters email

Plus the join code, if the link is code-protected. The code is a separate secret from the URL.

05Verifies the email

One click in the inbox. On by default, and the reason typos don't become support tickets.

06Sets a credential

Password or passkey. The account now exists in the identity realm — but holds no access yet.

07Reviewed link?

Yes → an explicit "waiting for approval" screen, not an empty state. Admin decides; email either way.

Branch
08Lands in the solution

Role granted, and the per-link redirect drops them on the role's entry screen — never a generic console.

"A public URL where he decides what to sign up as"

Worth being precise here, because there's a version of this that is safe and a version that isn't. Free choice of role is not on the table — no product reviewed offers it, and it would let anyone award themselves Solution Admin. But one URL that offers a choice between roles the admin has published is fine, and it's probably what you want for distribution: a single address to put on a poster.

Model it as a role-selector page that fans out to N registration links. The joiner sees "Join as Professor" / "Join as Student" and picks; behind each button is its own link, with its own screening, cap, expiry and audit trail. Only allowlisted roles ever appear, so Solution Admin is not a button that exists. One URL to hand out, unchanged security model — see D10.

End user · Professor

Log-in — when they have more than one solution

The case that breaks naive designs: the same person can hold different roles in different solutions — Professor in one, Student in another. Role is per-solution, so the session needs a solution context before it can render anything.

01Opens a login URL

Either the solution's own login URL, or the generic org login. Which one they use changes step 3.

02Authenticates

Password, passkey or the org's SSO. Identity only — this step knows nothing about solutions.

03How many solutions?

A solution-specific URL skips ahead. A generic login has to ask.

Branch
04aExactly one → straight in

Never show a picker with one option. Most end users are in this branch forever.

04bSeveral → picker

Each solution listed with the role they hold in it. Without the role, the list is ambiguous.

05Enters the solution

Session now carries a solution context; permissions resolve against that solution's role.

06Switches without logging out

A persistent switcher. Re-authenticating to change solution is the failure mode to avoid.

This journey has a dependency — D8

How deep the picker goes is not decided yet. If one email can hold accounts in two organizations, the picker needs an organization level above the solution level, and step 3 becomes a two-stage question. If it can't, solution-level is enough and this stays simple.

That's a Keycloak realm-configuration fact nobody has looked up. It is cheap to answer now and expensive to discover after the picker is built — so it should be closed before this journey is specced.

Implementation · 04

The five surfaces

1 · Link management — Solution settings → Access → Registration links

A table, because it's a list of objects. Columns: name, role, screening, uses (47 / 200), expires, status. Row actions: copy link, copy join code, pause, regenerate, revoke, view joiners. The empty state should teach the model in one line — "Registration links let people join this Solution without you knowing their email address. Each link grants one role."

Uses and expiry are columns, not settings — per D5, the bound has to be legible without opening anything. A capped link that has stopped admitting people looks exactly like a link nobody is clicking, and that ambiguity is the whole of Discord's documented failure.

2 · Create / edit drawer

Ordered the way an admin actually thinks: name → role (with a permissions preview — this is the moment to prevent a mistake) → who can join (the three presets, Custom behind a disclosure) → limits (pre-filled bounded, e.g. 30 days and 100 uses, with an explicit "no limit" opt-out) → where they land (an optional redirect URL, so the joiner arrives at the role's entry screen instead of a generic console — Keycloak does this on invitation acceptance, and it costs one nullable field).

Then a result preview, written as a literal sentence:

"Anyone with this link who verifies their email and enters the code can join Intro to Biology as a Student, until 12 Sep 2026 or 100 joins."

If the admin can't read that sentence and agree with it, the form has failed.

3 · Joiner landing page

Public and tenant-branded. It must answer three questions above the fold: what am I joining (Solution + org + logo), as what (the role, in plain language, with what it lets them do), and what happens next — especially for Reviewed links: "Your request will be reviewed by an administrator. You'll get an email when it's decided." Nobody should submit a form and land in a void.

Error states must be non-enumerating and human. Expired, revoked, exhausted and nonexistent all render the same message: "This link is no longer active — ask whoever shared it for a new one." Distinguishing them leaks whether a token ever existed.

4 · Approval queue

One inbox, scoped to the Solution: email, link used, requested role, submitted time, bulk approve/reject with an optional reason. Rejected joiners get a neutral email, never an accusatory one — the most common reason for rejection is a typo'd address.

Two states that are easy to get wrong. While a request is pending, the account exists but holds no access to the Solution — the joiner sees an explicit "waiting for approval" screen, not a broken empty state. And rejection must free the email for re-application, or the typo that caused the rejection becomes permanent and the person has to contact support to exist.

5 · Notifications — our existing surface

This is where the Canvas complaint gets fixed, and it fits the Notification Center already built:

  • Digest, not per-join. 200 students joining must not produce 200 notifications. "12 people joined Intro to Biology today."
  • Immediate for anything anomalous: approval requests, a link at 90% of max uses, a link that has just been exhausted, a link about to expire with recent activity, a burst of joins from one IP. The exhaustion notification is the one that matters most — it's the difference between "the link filled up" and "nobody signed up," which an admin otherwise cannot tell apart.
  • Always immediate for revoke and regenerate, to all Organization Admins. Link rotation is a security event and every admin should see it, including the one who did it.
Implementation · 05

Security requirements

Non-negotiable. Drawn from OWASP guidance on one-time tokens, account enumeration and rate limiting.

  • Token entropy ≥ 128 bits, CSPRNG, URL-safe. The token is the credential.
  • Encrypted at rest and re-revealable. Hashing plus a one-time reveal is stronger, but a link that can't be re-copied will be worked around by pasting it into a shared doc — a worse outcome. Recommend encrypted-at-rest; confirm with security.
  • Join codes are separate from the token and are the second factor for the Code-protected preset. They're short and brute-forceable, so rate-limit attempts aggressively — lock the link, not the IP, after N failures, and notify the admin.
  • Atomic use counting. UPDATE … SET use_count = use_count + 1 WHERE id = ? AND (max_uses IS NULL OR use_count < max_uses), then check rows affected. A SELECT-then-UPDATE overshoots the cap under concurrency — and a lecture hall scanning a QR code simultaneously is exactly that case.
  • Rate limiting per token, per IP and per email on every public endpoint, plus CAPTCHA on submit. An open registration endpoint on the internet will be found.
  • Auto-pause on abuse, don't just throttle. On a brute-force pattern against the join code, move the link to PAUSED and alert the owner. Throttling alone leaves an attacker grinding indefinitely at a slower rate against a link nobody is watching; pausing converts a silent attack into a notification. This is the reason PAUSED exists as a state the system can enter, not only the admin.
  • Incident response is a filter, not a spreadsheet. "Review everyone who joined via this link" has to be one click, with bulk deactivate — because storing joined_via_link_id on the membership makes it a single query. Discord makes you do this member by member, which is why leaked-invite cleanup there is a known ordeal.
  • No enumeration. Identical response body and identical timing for invalid, expired, revoked and exhausted tokens.
  • Full audit trail — create, edit, pause, resume, regenerate, revoke, approve, reject, with actor, timestamp and before/after — plus per-join attribution, so a leaked link's blast radius is one query.
  • Global kill switch at org level: "Disable all registration links." Immediate, no per-link cleanup. Every product in the study has one.
  • Block when an authoritative sync owns the users. Canvas disables self-enrolment when a course has an SIS ID, because self-enrolment would corrupt the sync. The same applies to SCIM/IdP-driven end-user provisioning: block it or make the admin explicitly acknowledge it.

Who can create links

Both the Organization Admin and the configurator need to work here, so split policy from operation — the Organization Admin sets the envelope, the configurator works inside it. This gives the security control without making the Organization Admin a bottleneck for every cohort.

Canvas is the precedent, and it's an exact structural match. There, the institution admin must enable self-enrollment at the account level before any instructor can switch it on for a course. Two levels, the upper one a capability gate, the lower one the operational use. That maps onto Organization Admin → Configurator with nothing left over — worth citing in the spec, because it means we're not inventing a permissions model, we're adopting one that an LMS already runs at institutional scale.

Implementation · 06

Phasing

V1 is scoped to everything the professor / Solution Admin / student scenario actually needs, and nothing else. The effort tags are for sizing the conversation, not estimates.

Settled — D1

The approval queue is in V1. The second research pass argued for deferring it to Phase 3; that was rejected, because without approval there is no Reviewed preset and therefore no safe way for a link to grant anything beyond the most basic role. It remains the largest single item in V1 — if V1 has to shrink, this is where the pressure will land, and the cost of cutting it is the Reviewed preset and elevated-role links.

V1 — walking skeleton

The full scenario, end to end

  • M Registration link as a first-class object; N per Solution, one role each
  • S Organization Admin allowlist of link-joinable roles per Solution
  • S Presets: Open / Code-protected / Reviewed
  • M Email verification, join code, expiry, max uses — bounded defaults, always visible on the link row — D5
  • S Pause, revoke, regenerate, plus the global kill switch
  • L Admin approval + approval queue — confirmed, D1
  • M Public tenant-branded landing page, incl. the existing-account join path
  • S Per-link redirect into the Solution — D7
  • M Notifications: join digest, immediate on approvals and rotation
  • M Audit trail and per-join attribution

V2 — hardening & scale

What institutions ask for second

  • M Domain allowlist / blocklist — highest-value V2 item; "deny public email providers" is the real ask
  • S QR code generation — the lecture-hall case, trivial once the link exists
  • M Incident response — joined-via-link filter and bulk deactivate
  • S Auto-pause on brute-force, with owner alert
  • S Assign runtime groups alongside the role
  • M Seat and entitlement warnings at creation — D9
  • M Bulk approve/reject; delegate approval to a named approver
  • S CSV export of joiners
  • M Per-link funnel: views → submits → completes

V3 — advanced

Where FlowX can go and nobody else can

  • Custom registration fields — student ID, department — into cas_user_attribute, with approval routed on their values
  • Approval as a FlowX process. Make the join-approval step a BPMN workflow the customer designs. No product in this study can do this — it's the native differentiator
  • Auto-expiry tied to the Solution's own lifecycle, e.g. a term end date
  • Auto-deprovision on expiry for time-boxed cohorts
Scope guard

What this is not

Every item below came up in research and is deliberately excluded. If one of these gets argued into V1, it should replace something, not extend it.

Not a replacement for targeted invitationsEmailing a named professor stays the right tool for three named people. This is for the 300 you don't have addresses for. Both ship, side by side.
Not free choice of roleNo product studied lets a joiner name their own role. The admin decides which roles exist as options; a joiner may pick between published ones on a selector page (D10), but never type or request an arbitrary role.
Not role-after-join sortingSlack's "everyone lands as a member, sort them later" model is explicitly rejected — it re-introduces the manual step this feature exists to remove.
Not a self-service org signupThis grants access to an existing Solution inside an existing organization. Creating an organization is a different flow with different commercial consequences.
Not SCIM or IdP provisioningWhere an authoritative sync owns the end users, self-registration must be blocked, not reconciled. Canvas's SIS rule is the precedent.
Not a bulk import toolCSV upload of 300 students is a separate, legitimate feature. It solves the same problem a different way and shouldn't be smuggled in here.
Before build

Open questions

These are facts we don't have, not opinions we haven't formed — each one needs someone to go and look. Anything that is a judgement call lives in Decisions instead, so the two don't get argued in the same breath.

  1. How is cas_runtime_role actually scoped? It is org-scoped, but the link needs to grant a role that means something within one Solution. If the assignment can't carry an application_id, D6 has only one possible answer. Owner: engineering.
  2. Can one email hold end-user accounts in two organizations? Decided by Keycloak realm configuration, not by us. Determines the existing-user join path. Owner: engineering. Feeds D8.
  3. Which Keycloak version do target releases ship? Organizations and invitation-only self-registration landed in 26.0. Even though we're not building on them, it changes what we can lean on for email verification and what we must own. Owner: engineering.
  4. Is there a seat/entitlement API we can query before provisioning? If not, D9's "block at redemption" isn't implementable in V1 and the answer becomes warn-only. Owner: engineering + commercial.
  5. Do any target customers already run SCIM or IdP provisioning for end users? If yes, the block-when-synced rule stops being theoretical and needs a V1 detection path. Owner: product.
  6. Should links work against SANDBOX and STAGING workspaces at all? A link leaked from a sandbox that shares a realm still mints a real account. Owner: product + security.
